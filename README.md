# Poseidon2 for Solidity, byte-identical to Noir

A pure-Solidity Poseidon2 over BN254 (`t = 4`) that computes **the same hash Noir does**, verified
against vectors generated by `nargo` rather than by restating this implementation.

```solidity
import {Poseidon2} from "poseidon2-sol/src/Poseidon2.sol";

bytes32 leaf = bytes32(Poseidon2.hash2(a, b));
uint256 root = Poseidon2.hash(inputs);
```

No dependencies. No FFI to run the tests. `forge test` on a clean checkout.

---

## Why this exists

If your circuit hashes in Noir and your contract hashes in Solidity, the two implementations must
agree exactly. When they do not, you do not get an error — you get a Merkle tree the circuit can
prove against and the contract computes differently. Deposits land at leaves the contract cannot
reproduce, withdrawals verify against roots that never existed, and the failure surfaces as funds
that cannot be moved.

That is a fund-loss-class bug, and it is easy to write. Poseidon2 has several published parameter
sets and more than one sponge convention. Picking the wrong combination gives you a hash function
that is perfectly correct and not the one your circuit uses.

This implementation targets exactly one thing: **barretenberg's `Poseidon2Bn254ScalarFieldParams`
(tag `v5.2.0`)**, which is what Noir's `std::hash::poseidon2_permutation` blackbox actually
executes. Parameters are `t = 4`, `d = 5`, `rounds_f = 8`, `rounds_p = 56`, and the round constants
were machine-extracted from `poseidon2_params.hpp` rather than transcribed.

## The test that matters most

```solidity
/// @dev The boundary case: 3 elements exactly fill RATE, so Noir skips the final
///      permutation. A port that permutes unconditionally passes every other test here
///      and still computes wrong roots. Do not delete this one.
function test_Hash_ThreeElements_ExactChunk() public pure
```

An input whose length is an exact multiple of the rate is the case that separates a correct port
from a plausible one. A implementation that permutes unconditionally at the end agrees with Noir
on one, two and four elements — and disagrees on three, six, nine. If you write your own, test
that case first.

## What is verified

`test/Poseidon2Parity.t.sol` — seven fixed vectors produced by `nargo` executing the same blackbox
`bb` runs. These are ground truth, not a restatement of this code.

`test/Poseidon2Sweep.t.sol` — a broader sweep across seeds and input lengths, including collision
checks.

Both are frozen constants, so the suite runs with nothing installed but Foundry. Regenerating them
needs Noir:

```sh
cd vectors && nargo execute --package vectors out
```

The `vectors/` directory contains the Noir program that produces them, so you can re-derive every
number here rather than trusting it.

## API

| Function | Purpose |
|---|---|
| `permute(uint256[4]) → uint256[4]` | The raw permutation |
| `hash(uint256[]) → uint256` | Sponge over an arbitrary-length input |
| `hash2(uint256, uint256) → uint256` | Two-element hash, for Merkle nodes |

All `internal pure`. The library has no storage and no external calls.

## Gas

Approximately **77k** for `hash2` and **135k** for a four-element `hash`, measured through an
external call with the call overhead and storage write subtracted. (`forge test` reports somewhat
higher numbers for the assertion tests — those include harness overhead, so do not quote them as
the library's cost.)

Poseidon is expensive on EVM. That is inherent to hashing in a prime field over 64 rounds, not
specific to this implementation. If you are hashing a depth-24 Merkle path on chain, budget
roughly 1.8M gas for the path alone.

## Provenance

Extracted from [ArcLite](https://github.com/UseArclite/ArcLite), a private batch-auction venue for
tokenized real-world assets, where it backs an append-only commitment tree of depth 24 and is the
hash the settlement circuit is proved against.
